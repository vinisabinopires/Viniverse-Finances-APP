Goal of this phase:
Add recurring transaction support so the user can create recurring income and expense rules, then generate transactions from those rules without duplicates.

Important constraints:
- Keep everything local-first using IndexedDB/Dexie.
- Do not add backend, authentication, Firebase, Supabase, or paid APIs.
- Avoid heavy libraries.
- Do not break existing accounts, transactions, budgets, backup/import/export, or onboarding.
- Do not rebuild the app.
- Do not add another bottom navigation item. Keep recurring transactions accessible from More/Settings.

Core concept:
Create recurring rules separately from actual transactions.
A recurring rule is a template. Generated transactions are normal transactions linked back to the recurring rule.

1. Database changes
Upgrade Dexie safely to the next schema version and add a recurringRules table.

RecurringRule fields:
- id
- name
- type: INCOME or EXPENSE
- amountCents
- currencyCode: USD or BRL
- accountId
- category
- description
- notes optional
- frequency: WEEKLY, BIWEEKLY, MONTHLY, YEARLY
- startDate
- endDate optional
- dayOfMonth optional for monthly/yearly rules
- dayOfWeek optional for weekly/biweekly rules
- isActive boolean
- createdAt
- updatedAt

Also add optional fields to Transaction if needed:
- recurringRuleId optional

Important:

- Existing backups without recurringRules must still import correctly.
- Clear All Data must clear recurringRules too.

2. Duplicate prevention
Generated recurring transactions must never duplicate.
Use a stable recurringOccurrenceKey, for example:
recurringRuleId + ":" + occurrenceDate

Before generating a transaction, check whether a transaction with the same recurringOccurrenceKey already exists.
If it exists, do not create another one.
